# Pull Request Checklist

## Purpose

This checklist helps reviewers and contributors validate changes before merging code.

A pull request should make the change easy to understand, review, test, and approve.

## Before Creating a Pull Request

- The branch name is clear.
- The change is focused and not too large.
- The code compiles or runs correctly.
- The main scenario was tested.
- Sensitive information is not included.
- Documentation was updated if needed.
- The pull request has a clear title.
- The pull request description explains the purpose of the change.

## Pull Request Description

The pull request should explain:

- What changed
- Why it changed
- How it was tested
- Risks or considerations
- Screenshots or examples, if applicable
- Related issue, task, or business requirement

## Review Checklist

- Code is readable and maintainable.
- Business logic is clear.
- Error handling is considered.
- Security and privacy risks were reviewed.
- Tests or validations were performed.
- No credentials, tokens, or private data are included.
- The change is aligned with the requested scope.
- The change does not introduce unnecessary complexity.
- Documentation is updated when relevant.

## Approval Criteria

A pull request should be approved when the change is understandable, tested, aligned with the objective, and does not introduce unnecessary risk.

## When Not to Approve

A pull request should not be approved if:

- The purpose of the change is unclear.
- The change is too large to review properly.
- There is sensitive information included.
- Testing evidence is missing.
- The implementation creates avoidable risk.
- The code is difficult to maintain.
- The change does not match the expected requirement.

## Good Review Practices

- Review the intent before reviewing the details.
- Ask questions instead of making assumptions.
- Suggest improvements clearly and respectfully.
- Focus on maintainability, clarity, and business impact.
- Avoid approving changes only because they "seem fine".
